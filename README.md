# デモ準備用

## プロジェクトの背景と理由

> どういう経緯でこのプロジェクトをするに至ったか，このシステムがどのように有益であると考えたか，何を実現しようとしたのか．

### 経緯
- 日々の生活に関連しているものの可視化を考えてた
- 一人暮らしで自炊をする際に、余った食材を活用できるといいと感じたから。
- 既存の料理サイトが可視化に特化しておらず、若干見づらくて検索性があまりなく不便であったから。
    - 既存のサイトは「作りたい料理の名前」や「食材1つ」で検索し、結果を一覧で1件ずつ見ていく形が中心である。
    - 冷蔵庫にある複数の食材から考えたいときや、時間・値段・栄養を見比べて決めたいときに、何度も検索し直す必要がある。

### 何を実現しようとしたか
- 持っている食材を入れるだけで、「今すぐ作れる料理」と「あと1〜2個買い足せば作れる料理」が一目で分かること。
- 候補の料理を、調理時間・値段・栄養・味などの軸で並べて、比べながら選べること。
- 「何を買い足せば作れる料理が増えるか」が分かり、買い物の判断にも使えること。

### どのように有益か
- 食材を使い切りやすくなり、食品ロスや無駄な買い物を減らせる。
- 献立を考える手間が減り、自炊を続けやすくなる。
- 料理名を知らなくても、手元の食材と条件(時間・入れたくない食材など)から料理に出会える。
- 既存の料理サイトと異なり、グラフを用いて料理の候補を提示するため料理を見つけるのが容易になっている




## システムのデモ
>  その場でシステムが動いていることを示す．想定される使われ方とともにシステムの機能を紹介する．
- 検索例を見せる
- 想定される使われ方2通り
    - 今あるものを活用するパターン
    - 買い足し前提のパターン
- お気に入り機能
- 類似度マップ
    - お気に入りのおすすめに活用されているアルゴリズム

このパターンを分けた理由は、今あるものを活用するパターンだと上位に買い足しが不要なレシピが出てしまって、買い物をするシーンには合わないと感じたから


## システムのデザイン
> 可視化方法に対する理由，利点．ほかの考えうる方法と比べてよいところはどこか．

既存のレシピサイトは1つの食材に対するレシピを提示するのが主流である

既存のサイトは複数の食材で検索できても、結果は一覧で並ぶだけで、時間や足りない食材の数で見比べることはできない

レシピ同士を比較検討できないと考えられる。

また、既存のレシピサイトは何か食べたい料理などユーザが能動的に決定をする必要があるが、私たちが作ったサイトではユーザが自分の情報(使える食材、使えない食材、持っている器具など)を入力するだけでサイトが能動的にユーザに対して提案をすることができる。

加えて、ヒートマップや散布図、グラフ、レシピ同士の類似性を可視化するような既存の例は存在せず、独自性があると考えられる。

可視化においては所要時間を最も重要視した。理由は、自炊をする上で一番気になるのは調理にかかる時間であると判断したためである。その他、栄養や費用なども可視化において比較検討できるようなデザインをした。



## 実装
> どのような実装を行ったか．どのような工夫を行ったか．データセットはどのように収集し，どの程度の大きさや情報の種類を得たか．

ユーザーが入力した「今ある食材」を正規化済みの食材名・別名と照合し、各レシピに対して不足している食材数を計算することで、買い足しなしで作れる料理と、少ない買い足しで作れる料理を比較できるようにした。

検索画面では、食材、避けたい食材、代用可能な食材、調理時間、価格、栄養、旬、使用器具、料理の系統・区分などを組み合わせて絞り込める。料理詳細では、表示人数に合わせて材料量を再計算し、個数・枚数などは分数を維持し、g・mlは四捨五入した整数として表示する。適量など推定を含む値は「目安」と明示し、元レシピの人数と現在の表示人数も区別している。

多数の候補を同時に扱うため、散布図は縮小時に料理の密度をヒートマップで示し、上位の候補を点として重ねて表示する。拡大時には表示範囲内の料理を系統ごとの半透明な点として展開し、拡大率に応じて点を大きくすることで、全体の傾向と個別の料理の両方を確認しやすくした。

また、買い足しなしで作れる料理は調理時間順のランキングとして提示し、複数の料理を調理時間・価格・使用食材数で比較できるようにした。さらに、材料・味・栄養・調理時間などの特徴を用いた類似料理検索と類似マップを実装し、料理どうしの近さを探索できるようにした。

散布図による可視化において、レシピデータの調理時間は５分刻みであるなど、そのまま可視化をしてしまうと点が潰れてしまったり混み合ってしまったりしてとても見辛かったため、ヒートマップを活用したり、見える点の数を制限したりするなどして工夫をした。

データセット(レシピ、レシピ写真)の収集はデリッシュキッチン([リンク](https://delishkitchen.tv/))をスクレイピングした。2468件のレシピが収集されている。レシピの選定では、「和食を中心として、日常的に作れるような料理で、材料も比較的準備しやすいもの」を中心にした。

### データの規模
- レシピ 2468品(全品に写真あり)
  - 分類: 主食 470・主菜 1014・副菜 571・汁物 195・デザート 218
  - 系統: 和風 1303・洋風 789・中華 229・韓国風 101・エスニック 25・インド風 12・メキシカン 9
- 食材 491種類(うち、代わりに使える食材があるもの 61種類)
- 材料の行 9340行、調味料の行 12238行、作り方の手順 10922手順

### データの出典
| データ | 出典 | 使い方 |
|---|---|---|
| レシピ(料理名・材料・分量・作り方・調理時間・費用目安・栄養・写真) | DELISH KITCHEN(https://delishkitchen.tv/) | 利用規約を確認し、禁止されていなかったので5秒程度の間隔を空けながらスクレイピングを実行した。公開・再配布はしない |
| 栄養の計算(サイトに値がないレシピだけ) | 文部科学省「日本食品標準成分表2020年版(八訂)」(JSON 化したデータ: [katoharu432/standards-tables-of-food-composition-in-japan](https://github.com/katoharu432/standards-tables-of-food-composition-in-japan)、CC BY 4.0) | 材料ごとに可食部100gあたりの値から計算 |
| 費用の計算(サイトに値がないレシピだけ) | 東京都総務局統計部「東京の物価」主要品目の東京都区部小売価格 2026年7月(CC BY) | 100gあたりの値段に直して計算。統計にない食材は同じ食品群の中央値 |

使ったライブラリ・モデル:
- D3.js v7(可視化)
- pykakasi(材料名の読みがな。検索の候補に使う)
- Ollama で動かしたローカル LLM の qwen3:30b(味の判定)
- Qwen3-Embedding-8B(レシピの文章の埋め込み。似ている料理の検索に使う)、umap-learn(類似マップの配置)

### 推定した値
サイトに書いてある値をそのまま使うことを基本にした。サイトにない値だけを推定し、どのレシピのどの値を推定したかを、データの各レシピの `estimated` などの項目に記録している。

| 値 | サイトの値 | 推定した値と、推定のしかた |
|---|---|---|
| 調理時間 | 2461品 | 7品はサイトに書いていないため、手順の文中の時間(「10分煮る」など)と手順の数から推定。120分を超える料理(冷やす時間を含むお菓子など、96品)は120分として表示 |
| 栄養(カロリー・たんぱく質・脂質・炭水化物) | 2411品 | 57品は成分表から計算 |
| 1人前の値段 | 2413品 | 55品は東京都の小売価格から計算。また、人数が書かれていない288品(「4個分」など)は、人数を推定してサイトの費用目安を割った |
| 味(甘さ・辛さ・酸っぱさ・しょっぱさ・こってり度、0〜5) | なし | 全品を qwen3:30b で判定。料理名・材料と調味料の量・作り方を渡して数値だけを答えさせた |
| 分量が「適量」「少々」の材料 | — | 1232品に含まれる。同じ材料のほかのレシピでの分量の中央値で補った。表示はサイトの表記を残し、補った値は「適量(目安: 1/4本)」のように目安として添える |
| アレルゲン(特定原材料8品目) | なし | 材料と調味料の名前から判定した目安。市販品の原材料は商品で違う |
| 調理のタグ(レンジだけ・火を使わない・ワンパン) | なし | 作り方の文章から判定 |
| 代わりに使える食材 | なし | 自分たちで表を作った(`temp_koba/delish_pipeline/substitutes.csv`。見直しの理由は `substitutes_review.csv`) |

成分表・小売価格からの計算値は、サイトの値があるレシピでも参考として残してある(`site_values.computed`)。最初に取った91品で比べると、カロリーの計算値はサイトの値とおおむね合い(比の中央値 0.99)、値段の計算値はサイトの値のおよそ1.4倍になった。サイトの費用目安は、安売りに近い値段を想定していると思われる。

作り方は `temp_koba/delish_pipeline` にまとめてある(詳しくは [data/readme.MD](data/readme.MD))。
